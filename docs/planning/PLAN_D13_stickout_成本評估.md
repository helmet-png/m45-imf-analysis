# D13：凸出星比例（stick-out fraction）當第二條 f_bin 制約的成本評估

**背景**：見 `LIMITATIONS.md` D13、`WORK_BOARD.md` B/C/D 類補齊表
`stick_out_fraction_constraint`。這是一份**成本評估**，不是實作——
按 WORK_BOARD 的驗收標準，先評估值不值得動 `pipeline/joint_fit.py`
核心似然函數，不建議未評估先動手改。

## 現狀

`pipeline/joint_fit.py:log_likelihood()`（440-449 行）只有一個似然項：
`poisson_loglike(obs_h, mod_h, ...)`，比較觀測跟合成的 Hess（CMD 密度
格點）圖。`f_bin` 是聯合六參數擬合裡唯一由這個似然項制約的自由參數，
沒有第二條獨立資訊。

專案裡已經有一條**逐星、CMD 偏移量**的雙星判定路徑可以重用：
`config.toml` 的 `cmd_offset_threshold=0.375`／`binary_offset_mag=0.753`，
被 `run_pipeline.py`（step4 四法雙星判定之一）跟
`verify_binary_detection.py` 使用——判定邏輯是「主序以上偏移超過門檻
星等」的逐星二元標記，跟 Hobart et al. 2026 的 `f_SO`（凸出星比例）
概念相同，不用重新發明分類邏輯，只是目前這個結果**沒有被餵回擬合**，
只當事後交叉核對用。

## 要新增什麼

1. **合成端**：`synthesise()` 已經生成合成星團的完整光度，加一個函式
   套用同一套 `cmd_offset_threshold` 邏輯，算出合成星團裡的凸出星比例
   `f_SO_model(theta)`——這步計算量小（跟現有 Hess 分箱同一批合成光度，
   不需要重新抽樣），程式改動集中在 `synthesise()` 回傳值或
   `log_likelihood()` 內部，不需要碰生成邏輯本身。
2. **觀測端**：套用同一套邏輯在真實 CMD 上算出 `f_SO_obs`（一次性、
   常數，不隨 theta 變），可以直接重用
   `verify_binary_detection.py` 或 `run_pipeline.py` step4 現有的
   逐星判定函式。
3. **新似然項**：`f_SO_obs` 是「N 顆星裡 k 顆是凸出星」的比例，用
   Binomial(k; N, f_SO_model(theta)) 或其常態近似當第二個似然項，
   跟現有 Poisson-Hess 似然項相加（log 空間直接相加）。
4. **相對權重**：Hess 似然項有 `nb_c * nb_m` 個格點的資訊量，凸出星
   似然項只是一個純量——直接相加可能讓凸出星這一項的訊號被 Hess 項
   淹沒（不起作用）或反過來因為 Binomial 在小 N 下方差小而意外過度
   主導，兩種都要先用注入回收測過權重才能用，不能假設「加了就有效」。

## 成本估計

| 項目 | 估計 | 備註 |
|---|---|---|
| 合成端新函式 | 小（半天內） | 重用現有偏移判定邏輯，純函式 |
| 觀測端 | 幾乎零 | 直接呼叫既有函式算一次常數 |
| 似然項整合 | 中 | 要決定 Binomial vs 常態近似、要不要加權重超參數 |
| **驗證（必要，不能省）** | **中大** | 比照 dav 的教訓（見 `LIMITATIONS.md`
可辨識性一節）：新自由度或新似然項放進模型前，必須先用注入回收驗證
「這個新資訊真的能收緊 f_bin 的後驗」，不能假設加了就有效。至少要
跑一組「用常數 f_bin vs 質量相依 f_bin」的注入回收（比照
`mass_dependent_fbin` D14 衍生條目的作法）比較有/沒有這條似然項時
`f_bin`／`alpha` 的後驗寬度差多少 |
| 全部數字重跑 | **大** | 如果驗證通過、決定採用，`p2_final2_v3` 等
所有headline 數字都要用新似然函數重跑，不是加了就能沿用舊結果 |

## 建議

**先做驗證性小實驗，不要直接改生產似然函數**：

1. 先只做「觀測端凸出星比例」這個診斷數字本身（重用既有函式，幾乎零
   成本），量出 M45 real data 的 `f_SO_obs` 是多少、乘上樣本數看看
   有效資訊量（k、N-k 兩邊都要有足夠統計量，凸出星通常是少數，若
   k 太小這條似然項天生資訊量就低，值不值得加要看這個數字）。
2. 若 `f_SO_obs` 的統計量夠（例如 k>=20，Binomial 標準誤才不會大到
   淹沒訊號），再做一個獨立於生產程式碼的小型合成實驗：手動生成
   兩組合成星團（f_bin 不同、其餘參數固定），比較兩者的 Hess 似然
   打分是否能區分，跟凸出星似然打分是否能區分——如果凸出星似然的
   區分力明顯強過 Hess 似然在 f_bin 方向上的區分力，才值得投入
   步驟 3-4 的正式整合。
3. 只有上述驗證顯示「確實能收緊 f_bin」，才進到動
   `pipeline/joint_fit.py` 核心似然函數這一步，而且要先開獨立分支，
   全部 headline 數字要重跑才能採用。

**結論**：這不是一個「小改動、大概率有用」的任務，是一個「小驗證、
中不確定、若成立則大改動」的任務。建議下一個認領的人先做上面步驟 1
（幾乎零成本），憑那個數字決定要不要繼續，不要一次跳到修改生產程式碼。
