# M45 亮端星為什麼沒有進入 CMD？

## 一句話答案

對目前最清楚的一顆例子（Gaia DR3 `65205373152172032`，G = 4.173），原因已經可以定位：它在 **成員判定** 就得到 P = 0.0017，遠低於本專案 P >= 0.7 的門檻。因此它根本沒有被送到後面的 CMD 測光品質篩選。這不是 `g_bright_limit = 4.0` 把它切掉，也不能用 RUWE 直接解釋。

這只回答了「這一顆在哪一關離開」；**尚未**證明它本來應該被救回為 M45 成員，也尚未說明所有亮星都同樣如此。

## 這次做了什麼

沒有重跑任何完整計算，也沒有重新查 Gaia。只讀取兩個已存下來的中繼資料：

1. `results/baseline.dat`：pyUPMASK 已算完、但尚未套 P >= 0.7 門檻的表。
2. `data/cmd_members.csv`：套過成員門檻與第 2 步測光品質篩選後的表。

新腳本 `scripts/diagnostics/diagnose_m45_bright_end_loss.py` 會把指定的 Gaia `source_id` 對照這兩關，結果存成 `results/bright_end_loss_diagnosis.json`。

## 可重現結果

| 星 | G | 視差 (mas) | pyUPMASK P | 在 `cmd_members.csv`？ | 能確認的離開位置 |
|---|---:|---:|---:|---|---|
| `65205373152172032` | 4.173 | 7.067 | 0.0017 | 否 | 成員門檻前：P < 0.7 |
| `66529975427235712`（HIP 17851） | 5.203 | 7.241 | 0.9999 | 是 | 保留 |

在 `baseline.dat` 中，G = 4.0–5.203 的四筆資料裡，只有 HIP 17851 通過 P >= 0.7；其餘三筆的 P 都低於門檻。這個小樣本只能說明「亮端缺口至少有一部分出現在成員判定」，不是完整的外部成員清單。

## 為什麼不能直接怪 RUWE 或測光切割？

- `ruwe_threshold = 1.4` 在本專案是後續的聯星標記，不是成員表的排除條件。
- `65205373152172032` 已在 P 門檻前離開，所以它的 BP/RP、SNR 是否也會失敗，對它是否進入 CMD 沒有因果作用。
- 第 2 步的亮端切割只排除 G < 4.0；這顆 G = 4.173 不在該範圍。

## 仍未解決的部分

本機缺少原始 Gaia 表 `data/m45_r5_g18_plx4.csv`。因此目前不能逐顆檢查：

1. 外部目錄認定為 M45 成員的其他 G = 4.0–5.2 星，是否也都在 pyUPMASK 得到低 P；
2. 若某顆通過 P >= 0.7 卻沒有進 CMD，究竟是 G/BP/RP 訊雜比還是 BP/RP excess 切掉；
3. 低 P 是亮星聯星的天測量受擾，還是這些星並非本研究採用定義下的成員。

下一個最小步驟應是：拿 Hipparcos/外部成員表的 8–10 顆亮星 Gaia `source_id`，對原始 Gaia 欄位做一次小量查詢，然後用同一腳本逐關記錄。這比重跑整個 pipeline 便宜，而且能把「一顆範例」擴充成可檢驗的清單。

## 科學上現在可以怎麼說

可以誠實地說：M45 的亮端不完整風險不只來自刻意設定的 G < 4.0 截斷；至少一顆 G = 4.173 的外部候選星是在 pyUPMASK 成員機率關卡被排除。不能說：這顆必定是被錯殺的成員，或目前 IMF 的高質量斜率已被量化地偏移。
