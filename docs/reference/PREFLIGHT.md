# 開跑前檢查：為什麼要有，以及它擋的是什麼

這份文件記錄的判斷與數字都代表寫下當下的理解，不是不能動的規則（見
`CONTRIBUTING.md` 零之二）。發現哪一條站不住腳、或有更好的做法，直接改。
沿革見 [CHANGELOG.md](../../CHANGELOG.md)。

## 這套機制在防什麼

失敗的形狀分兩種。一種大聲、立刻、便宜——當掉、`CornerError`（貼牆
偵測），模型發現答案是被搜尋邊界決定的，當場拒絕輸出。另一種安靜、
`exit 0`、檔案正常寫出、數字長得像真的，但算法本身沒有照宣稱的方式
執行（例如 `--refines 3` 沒有真的精修，只回傳粗網格 argmax，見
`LIMITATIONS.md` A1）——這種失敗只能靠運氣被發現（例如有人注意到十二
次重複的結果精確相同）。這套三道關卡的設計目標，就是讓第二種失敗
也長得像第一種：**檢查「算出來的是什麼」，不是「旗標下對了沒」**。

一份宣告式的檢查表（「確認有帶 `--refines 3,3`」）在旗標本身沒錯、
但旗標的意思錯了的情況下會全部通過。唯一抓得到這類 bug 的方式，是
實際跑一次、量出來的結果跟預期對帳。同一個原則的推論：檢查程式不要
自己複製一份參數預設值與模型建構流程，否則兩邊會各自演化然後不同步
——A2／A3／B1／B2 因此做成五支計算腳本自己的 `--preflight` 旗標，
用它們自己的 parser、自己的模型建構，檢查到的必然就是真正會跑的
那組設定。

## 三道關卡

| 關卡 | 內容 | 在哪裡 |
|---|---|---|
| **A1** 解析度自我測試 | 峰值放在已知位置實跑一次搜尋，量它有沒有照宣稱的階數收斂；含反向對照與平行路徑一致性 | `scripts/tools/preflight.py --gate a` |
| **A2** 設定對帳 | 模型實際生效的值 vs `config.toml` 宣告的值，逐項比對 | 五支計算腳本各自的 `--preflight` |
| **A3** 網格涵蓋 | 搜尋軸有幾個粗格點落在等時線網格涵蓋之外（會被吸附成幽靈格點） | 同上 |
| **B1** 意圖對帳 | 這次實際會算幾項掃描（設定／冪次／污染比例／真值／情境）、幾次重複、幾階精修、實際格距 | 同上（五支都有，`preflight.workload_audit()`） |
| **B2** 輸出衝突 | `--tag` 對應的檔案是否已存在、manifest 設定是否相容 | 同上（五支都有，`preflight.output_audit()`） |
| **B3** 續傳能力 | 這支腳本撐不撐得過中途被砍 | `preflight.py --gate b`（五支都有，`scripts/tools/checkpoint.py`） |
| **C1** 量化簽章 | 最佳點是否全落在粗網格節點（可疑訊號，需搭配實際解析度或搜尋軌跡判定，不是必然＝沒精修）、重複間散布是否精確 0、有無貼牆 | `preflight.py --gate c` |
| **C2** manifest 完整性 | 沒有 manifest 的結果檔無法事後查證設定 | 同上 |

`run_queue.py` 已接上：派工前跑 B（不通過就記 `preflight_fail` 並跳過，
不燒機時），跑完 `ok` 後跑 C；Gate C 不過會把狀態改記成 `gate_c_fail`
（不是 `ok`），跟 B 一樣不放進 `read_done()` 的自動重跑白名單，避免
盲目重跑白燒一次已經花掉的機時。兩道關卡都不會讓整條佇列停下來——
沒過就跳過這一項，機器繼續跑下一項。

檢查焊進五支計算腳本自己的 `main()`，不是焊進呼叫端（`run_queue.py`）
——不管從哪台機器、用什麼方式呼叫（本機佇列、Kaggle 筆記本、x64
協作機直接執行），檢查一定會發生。`--preflight` 旗標的意思是「只
檢查、不要真的算」的乾跑模式，不加這個旗標時檢查一樣會自動跑一次，
有阻擋級問題就 `sys.exit(1)`，除非帶 `--force`（僅供已經看過警告、
確認要略過的情況使用，不是日常流程）。

## 五支腳本現在的涵蓋範圍

| 腳本 | A1 演算法本身 | A2 設定對帳 | A3 網格涵蓋 | B1／B2 意圖對帳／輸出衝突 | B3 續傳 |
|---|---|---|---|---|---|
| `fit_real.py` | 共用（`preflight.py --gate a`） | 有 | 有 | 有 | 有 |
| `profile_lowmass.py` | 共用 | 有 | 有 | 有 | 有 |
| `profile_outlierfrac.py` | 共用 | 有 | 有 | 有 | 有 |
| `inject_lowmass.py` | 共用 | 有 | 有 | 有 | 有 |
| `injection_recovery.py` | 共用 | 有 | 有 | 有 | 有 |

A1 是共用的：`multi_stage_best()` 是這五支腳本都在用的同一份搜尋演算法，
驗證它本身的正確性只需要做一次。A2／A3 集中在
`scripts/tools/preflight.py` 的 `audit_common()`，五支腳本呼叫同一份
邏輯，其中任一支的模型建構方式改變，其餘四支立刻一起受益。B1／B2
（`workload_audit()`／`output_audit()`）只認一組共同形狀（`scan_keys`
＋每個 key 重複幾次），每支腳本自己把旗標轉換成這組形狀再呼叫。B3
（續傳）的共用實作在 `scripts/tools/checkpoint.py`
（`atomic_savez()`／存取鎖／`load_partial()`／manifest 比對），五支
腳本都呼叫同一份，不維護各自的複本。`run_queue.py` 的
`PREFLIGHT_AWARE_SCRIPTS` 常數列出這五支腳本，Gate B（`_preflight_ok()`）
跟 `preflight.py` 的 `gate_b()` 都吃這個常數。

`checkpoint.save_progress()` 用一個 `attempted`（已嘗試次數，跟
`len(results)`／已成功次數分開記）處理 `inject_lowmass.py` 會遇到的
貼牆例外——某次試驗因為 `WallError`／`CornerError` 失敗，那個試驗
索引真的跑過一次，續傳時不該重跑（重跑只會用同一組亂數種子再得到
同一個失敗結果）。`injection_recovery.py` 的 `multi_stage_best()`
呼叫帶 `raise_on_wall=False`（貼牆只印警告不丟例外），每次嘗試必定
成功，不需要這層區分。

`expected_overrides` 機制：`profile_lowmass.py` 等四支診斷腳本會刻意
`cfg._data["joint_fit"]["mh_prior_sigma"] = 0.0` 關掉金屬量高斯先驗
——這是設計上正確的行為（先驗會污染這些腳本要測的東西），不是 A2
那種「該用先驗卻被悄悄關掉」的 bug。`audit_common()` 接受
`expected_overrides={"mh_prior_sigma": 0.0}` 這類參數，登記「這個鍵
本來就該是這個值」，但仍然檢查模型實際生效的值有沒有精確等於這個
刻意值——如果哪天那行覆寫被不小心刪掉或改動，這裡還是抓得到。

## 驗證方式

五支腳本各自 `--preflight` dry-run 過（含故意給不存在的設定／情境
名稱，確認阻擋正確觸發）；`checkpoint.py` 的 `save_progress()`／
`load_progress()`／`check_manifest()` 有單元測試（含跨行程競態、
legacy 檔案相容性、`gate_c()` 對 `__attempted_*` 記帳鍵的排除）；
`inject_lowmass.py`／`injection_recovery.py`／`profile_lowmass.py`
各自用假的 `multi_stage_best()`／`make_fake()`（跳過真正的合成星團
運算，只驗證存檔／續傳這條路徑本身）跑過完整的「執行一次→中斷→
重啟」流程，確認第二次執行時已完成的項目一律被跳過。沒有花機時去
真正等一次完整的診斷腳本跑完，這條路徑目前只驗證到「存檔／續傳的
機制本身正確」，不含「真正的擬合流程跑完全程不出錯」。

## 已知涵蓋缺口（不要把「放行」讀成「檢查過了」）

- B3 續傳目前只驗證到機制本身，沒有跑過一次完整的真實擬合流程去
  確認「續傳後接著跑的真實計算不出錯」。
- Windows 非預期重開機本身沒有處理——這是造成 B3 需求的根本原因，
  屬於機器設定不是程式碼，這次的修法是讓程式撐得過中斷，不是讓
  中斷不發生。
- A1 只測搜尋演算法本身。它驗證 `multi_stage_best()` 會照宣稱的
  階數收斂，不驗證概似函數、合成星團生成、選擇函數這些的正確性
  ——那些要靠注入回收，而注入回收測不到等時線的物理誤差（見
  `LIMITATIONS.md` C1）。
- 這套機制目前只有本機（x64 桌機）驗證過。Kaggle 筆記本與其他協作機
  在下一次真正用到這五支腳本時才會第一次實際觸發。

## 建立當下就抓到的問題

- **搜尋軸有一半是幽靈格點**：COARSE 的 logage 軸 `[7.30, 8.40]`，
  但預設 PARSEC 網格只涵蓋 `[7.70, 8.25]`，12 個粗格點裡有 6 個會被
  最近鄰吸附到邊界等時線，不是獨立的模型。初步判讀是維持現狀不要
  動：把 COARSE 收窄會改變搜尋空間，`_final` 就不能跟 `_prelim`
  直接對照；M45 的答案落在 logage≈8.03，在涵蓋範圍內部。
- **`radial_r1_prelim` 沒有 manifest**：跑在 manifest 功能加入之前，
  也漏帶 `--configs C`。config C 的 7 個參數裡有 4 個精確落在粗網格
  節點上，其他三個切片是 0/7（r2、rall）與 2/7（r3）。可能只是核心
  區樣本少（355 顆）、概似面平坦，精修後真的回到粗格點——但從存下來
  的 npz 分不出來，因為輸出只記最佳點、沒記達成的解析度。`radial_r1_final`
  （`--refines 3,3 --repeats 5`）重跑後這個疑慮會自然解掉。
